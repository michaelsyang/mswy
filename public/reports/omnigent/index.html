Omnigent: Analysis & Evaluation

Report date 26/08/23 · Repo data verified via GitHub API on 26/08/23 · Subject: github.com/omnigent-ai/omnigent · Status as evaluated: v0.10.0 (alpha)

What it is

Omnigent is an open-source meta-harness — an orchestration layer that sits above AI coding-agent harnesses rather than replacing them. It wraps terminal-based agents (Claude Code, Codex, Cursor, Pi, …) and SDK-based agents behind one uniform interface, then adds the things a single harness can't do: swapping harnesses without rewriting agent definitions, enforcing governance policies and OS sandboxing across all of them, real-time multi-user collaboration on live sessions, and access from terminal, web, phone, or desktop app.

"Omnigent is an open-source meta-harness that gives you a common orchestration layer over Claude Code, Codex, Cursor, OpenCode, Hermes, Pi, and the agents you write yourself: swap or combine harnesses without rewriting, enforce policies and sandboxing, and collaborate in real time from any device."

— README, omnigent-ai/omnigent, retrieved 26/08/23

The pitch, per the launch post by Matei Zaharia et al., is that frontier work has moved up a level: multi-model, multi-agent patterns (Harvey's worker+advisor split, Anthropic's lead-agent-with-subagents, Databricks' Genie) span harnesses, but each harness is its own silo. Omnigent provides three pillars — Composition, Control, Collaboration.

Who made it

Built and maintained by Databricks. Announced at Data + AI Summit and open-sourced under Apache-2.0 on 26/06/13; the GitHub repo was created 26/06/11. The launch post credits Matei Zaharia (Databricks CTO/co-founder, also creator of Apache Spark), Kasey Uhlenhuth, and Corey Zumar.

Development remains heavily Databricks-core: the top five contributors (PattaraS ~630 commits, TomeHirata ~350, serena-ruan ~320, dbczumar ~170, fanzeyi ~160 as of 26/08/23) account for most of the ~2,700 commits, though the contributor list exceeds 100 accounts overall. There is also a commercial sibling: "Omnigent on Databricks," a managed deployment covered by official Databricks documentation.

How it works

Four moving pieces:

  • Runner — wraps any agent in a sandboxed session exposing a uniform API ("messages and files in, text streams and tool calls out"). Each harness gets an adapter module (omnigent/inner/<name>_harness.py).
  • Server — persists sessions (SQL DB + Alembic migrations), enforces policies, handles auth/multi-user accounts, and exposes every session over terminal CLI, web UI, mobile app, and REST APIs.
  • Host — registers your machine (or a cloud sandbox) as an execution target the server can schedule onto.
  • Sandbox layer — per-platform OS isolation: bubblewrap on Linux, Seatbelt on macOS, Windows Job Objects (containment only — no filesystem/network isolation), plus disposable cloud sandboxes (Modal, Daytona, E2B, Kubernetes, Boxlite, CoreWeave, Databricks, and more).

Policies (the governance core)

Declarative gates evaluated at enforcement points, returning ALLOW / DENY / ASK. Multiple policies compose; a DENY short-circuits everything else. They stack across three levels — server-wide (admin) → agent spec (developer) → session (end user) — with session-level checked first.

policies:
  budget:
    type: function
    handler: omnigent.policies.builtins.cost.cost_budget
    factory_params:
      max_cost_usd: 5.00           # hard spend cap...
      ask_thresholds_usd: [3.00]   # ...with a soft warning on the way

Unlike prompt-based guardrails, policies are stateful and contextual — e.g., "after an agent runs npm install, require human approval before git push" or "only write to files it created." Full catalog in docs/POLICIES.md.

Agent definition

An agent is a short YAML file — prompt, tools (local Python functions, MCP servers, sub-agents), executor harness, policies. Swapping Claude Code for OpenCode or Codex is a one-line change to executor.harness. Example agents ship with the repo: Polly (multi-vendor orchestrator: plans, delegates to parallel coding sub-agents in git worktrees, cross-reviews each diff with a different vendor) and Debby (Claude-vs-GPT dual-head brainstormer with a /debate mode).

How to use it

Python 3.12+, macOS/Linux fully supported; Windows runs degraded via uv (no native sandboxing). Install and start:

curl -fsSL https://raw.githubusercontent.com/omnigent-ai/omnigent/main/scripts/install_oss.sh | sh

omnigent            # interactive session + local web UI on :6767
omnigent claude     # Claude Code in a shareable session
omnigent codex | cursor | opencode | hermes | pi
omnigent run examples/polly/          # multi-agent orchestrator demo
omnigent setup      # credentials: API keys, subscriptions, gateways (OpenRouter/LiteLLM/Ollama)

# team / remote use
OMNIGENT_AUTH_ENABLED=1 omnigent server --background
omnigent host https://your-server   # register this machine as a runner
omnigent attach <session_id>        # co-drive someone's live session

A local server is reachable on your LAN (phone included); Docker deploys cover VPS/cloud targets, with one-click recipes for Render/Railway/Fly.io/HF Spaces/Cloudflare. Model credentials come from vendor API keys, existing Claude/OpenAI subscriptions via official CLIs, or any OpenAI-/Anthropic-compatible gateway.

Supported harnesses

First-class = dedicated adapter modules shipped in the repo (omnigent/inner/, enumerated from the tree on 26/08/23). "-native" variants drive each tool through its own native protocol instead of the SDK, preserving tool-specific features (approvals, cost tracking, elicitation). Anything speaking ACP (Agent Client Protocol) can be attached as a configured external agent.

Engineering hygiene (from repo inspection)

  • ~2,120 Python files plus a React/TypeScript web UI, iOS/Android apps, Electron desktop shell, and a Rust dev supervisor — a large, actively-typed codebase with an ongoing mypy cleanup tracked publicly.
  • Unusually strong CI security posture for an alpha project: a deterministic PR security scan gates all CI for untrusted contributions (SECURITY.md), scanning for secret exfiltration shapes, reverse shells, and CI-workflow misuse.
  • Structured design docs, deprecation-version conventions, pre-commit + ruff, e2e test suites including PTY timing tests.

Community reception — thinner than the stars suggest

  • The strongest organic signal: r/databricks announcement, ~226 votes / 52 comments (26/07). Representative comment: "Omnigent is definitely leading on governance etc." alongside questions comparing it to OpenCode. On r/AI_Agents, one user: "That's why I'm also quite excited about omnigent. It helps me to switch between them easily. It's still in early stage but looks super promising."
  • Hacker News traction is weak: best submission 15 points / 4 comments (26/06/13); nothing above single digits since. ⚠️ Below typical thresholds for high-signal HN validation.
  • No independent benchmarks exist. All performance claims (e.g., keystroke echo cut "~250 ms → under 10 ms" in v0.10.0) are project-sourced. Coverage elsewhere (MarkTechPost 26/06/13, Addepto, Developers Digest 26/06/16) is derivative of the launch post.

Issues & gaps

Alpha software, explicitly. The repo badges itself status: alpha. Open issues+PRs grew from 825 → 1,188 over three weeks — mostly fast-turning polish bugs, but expect breakage between weekly minors.
  • OpenCode path is the least mature. Internal gap-tracker docs exist (designs/opencode-native-gaps.md), and as of 26/08/22 an open issue reports every relayed Omnigent tool call killed at 60s in opencode-native (#5265). Long-running tool calls through OpenCode will bite until fixed.
  • Governance regression in v0.10.0. Shared-session approval-authority restrictions were reverted: "session approvals are once again available to any shared editor, not just the session owner" (#4318). If you expose sessions to teammates, approval gating is weaker than it was in v0.8–v0.9.
  • Telemetry on by default. Anonymized usage collection ships enabled; opting out requires following separate instructions. Worth knowing before adopting in any sensitive environment.
  • Databricks gravity. Development direction, smart-routing defaults, and managed offering all orbit Databricks infrastructure. The OSS version keeps LLM-classifier routing, but roadmap items (AI Gateway routing, Lakebase-backed deploys) assume their ecosystem. Vendor lock-in risk is moderate, not severe — Apache-2.0 and one-line harness swaps limit blast radius.
  • Windows second-class. Native sandboxing absent (Job Objects only contain process trees), POSIX bootstrap script, dev unsupported natively.
  • Contribution concentration. Effectively a corporate-maintained single-org project so far; bus factor is fine while Databricks stays committed, but community ownership hasn't formed yet.

Verdict

✅ Try limited. Legitimate and unusually well-engineered for an alpha. Best fit: teams running more than one agent harness who want swappability, spend caps, and OS-sandboxed sessions under one roof. Skip if you run exactly one harness and already trust its own guardrails — the meta-layer adds operational surface without unique value there.

Practical guidance: pin to the latest minor (v0.10.0+), avoid opencode-native for anything with long tool calls until #5265 closes, review the shared-session approval default before collaborating, and disable telemetry if that matters to you. For a pure "does harness X handle our tasks" experiment, running X standalone is still simpler — Omnigent earns its keep when the same governed session must move between harnesses.
